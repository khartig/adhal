# Architecture

How Adhal is built: the modules, what each one owns, and how a drop moves
through them. The wire format is specified in
[`PROTOCOL.md`](PROTOCOL.md), and what it protects in
[`THREAT-MODEL.md`](THREAT-MODEL.md). How the design was arrived at,
including the measurements and the mistakes, is in
[`history/ENGINEERING-LOG.md`](history/ENGINEERING-LOG.md). This document
describes the code as it is; where a reason matters, it names the section
of one of those that gives it.

**Numbering.** `D1`-`D7` are the data-path steps below. `W1`-`Wn` are work
items in [`IMPLEMENTATION-PLAN.md`](IMPLEMENTATION-PLAN.md).

## Layout

Two workspace packages. `cli/` imports only from `@ad-hal/engine`, never
from Hyperswarm or hyperdht directly, so everything about the network and
the protocol lives in one place.

**`engine/src/`, the protocol and the transport:**

## Key hierarchy

```
Per-drop ephemeral announce keypair    <- generated by createSwarm, never persisted
Drop code = nameplate + secret
`-- PAKE (CPace) per connection -> ISK
    `-- k_r2s, k_s2r                   <- one Channel per transfer, wiped when it ends

Long-term identity (none today)        <- if ever added: inside the channel only
```

**The keypair a drop announces to the DHT is generated for that drop and
discarded with it.** `createSwarm` generates it itself and refuses one
from a caller (W15b), because the obvious way to build "keep this device"
is to persist that keypair, which would let DHT nodes link every drop one
person makes. See [`THREAT-MODEL.md`](THREAT-MODEL.md) §4.

## The data path

1. **D1, the code.** The receiver generates five words: a two-word
   nameplate, which is public and names the topic, and a three-word
   secret, which is the PAKE password and is hashed into nothing an
   observer can see (PROTOCOL §2). The CLI shows the code, and its QR
   symbol, only after its announce has flushed.
2. **D2, the rendezvous.** Both peers join the topic as server and client.
3. **D3, the handshake.** For each candidate connection: HELLO, REPLY,
   CONFIRM (PROTOCOL §3). A candidate that fails is discarded, and only a
   failed confirmation or a reused `sid` is counted.
4. **D4, the offer.** The sender sends the manifest; the receiver checks
   it, asks its person, and answers ACCEPT or DECLINE before any file byte
   moves (PROTOCOL §4.0).
5. **D5, the bytes.** CHUNKs, then END for a stream. A resumable transfer
   gets a CHECKPOINT every 5 s, after an fsync (PROTOCOL §7, §8.3).
6. **D6, verification.** The receiver checks the whole-file digest,
   publishes the file without replacing anything it did not create, and
   only then sends RESULT. The sender succeeds only on a RESULT carrying the
   digest it sent (PROTOCOL §4.2).
7. **D7, leaving.** Each side destroys its swarm. Forgetting a trusted
   peer belongs to "keep this device", which does not exist.

## Finding a peer: `swarm.js`

`createSwarm` makes a Hyperswarm with a fresh announce keypair, 16
parallel dials rather than Hyperswarm's 3 (stale announces otherwise starve
a live peer of any slot), and an `'error'` sink on every connection, so a
candidate that resets cannot take the process down.

`acceptOnce` (the receiver) and `connectOnce` (the sender) are the same
shape:

- **Join and refresh.** Both join with `server: true, client: true`. Both
  re-run the DHT lookup every 4 s (`REFRESH_INTERVAL`), because
  Hyperswarm's own schedule is ten minutes and loses a race that measurably
  stranded drops. The receiver reports `onAnnounced` only once its
  announce has flushed.
- **One handshake object per connection.** The `Initiator` or `Responder` is
  constructed inside the `'connection'` handler. That is what keeps the
  scalars and the `sid` per connection (PROTOCOL §3.2, trap #1), and there
  is no way to inject either.
- **Every candidate is bounded.** A 15 s handshake deadline
  (`HANDSHAKE_TIMEOUT_MS`), plus any backoff. A connection that has
  received no UDX packet after 5 s is dropped too
  (`UNANSWERED_CONNECTION_MS`). On a shared address hyperdht can report a
  connection open whose far end it has already discarded, and Hyperswarm
  then prefers that dead connection to a live one. `swarm.js` has the
  mechanism in full (W15d).
- **What is counted.** A failed confirmation goes to the `AttemptCap`. On
  the sender so do a reused `sid`, and any run it sent REPLY that did not
  answer with a valid CONFIRM: the sender reserves an attempt before each
  REPLY and settles it when the run ends (PROTOCOL §6). A close, a reset,
  a silent candidate, or a dead connection that was never sent REPLY is
  never counted. After a failure, the next HELLO (receiver) or REPLY
  (sender) is delayed by the backoff, and refused by nobody.
- **Pairing.** The first candidate to complete is resolved with its socket
  (paused, so nothing arrives before the transfer listens), any bytes read
  past the handshake as `pending`, the channel keys, and the negotiated
  capabilities.
- **After pairing, it keeps answering.** A late candidate runs the same
  handshake, deadline, backoff, and counting. One that confirms is sent
  `DECLINE{ERR_DROP_TAKEN}` as its only sealed frame and closed
  (`declineLate`). `stopAnswering()`, or destroying the swarm, ends this.
- **The two timeouts say different things.** `ERR_NO_PEER` means nobody
  connected; `ERR_NO_HANDSHAKE` means peers connected and none completed,
  which points at the handshake rather than the DHT.

## Without a swarm: `stream-handshake.js`

`acceptStream` and `connectStream` run the same handshake over one stream
the caller has already connected. They use the same `Initiator` and
`Responder`, so the parameter mapping exists in one place. They exist to
prove PROTOCOL §3.3's claim: the channel's security does not come from
the transport. The loopback CLIs run them over plain TCP, with no Noise
underneath.

There is one stream and one attempt, so there is no candidate management
and no attempt cap: a failed confirmation rejects, and the caller decides
what that costs. The loopback receiver ends the drop on it, which is an
attempt cap of one. A handshake that does not complete in 15 s is
`ERR_STALLED`, and a close before it completes is `ERR_CONNECTION`; both
carry `phase: 'handshake'`, so the CLI's report does not speak of bytes or
partials. The caller's socket is never destroyed here, and it is left
paused, with any extra bytes returned as `pending`, as `acceptOnce` does.

## The channel: `frame.js`, `message.js`, `channel.js`

Every frame after the handshake is
`[4-byte length][ChaCha20-Poly1305(k_dir, nonce, [type][body], aad = length)]`
(PROTOCOL §3.4, §5). The three modules split it:

- `frame.js` delimits by length and refuses a declared length over the cap
  (1 MiB) before buffering any of it. It knows nothing about the contents.
- `message.js` owns the type tags and every body's encoding. Its decoders
  either return a well-formed value or throw a code; the ones for CANCEL
  and DECLINE never throw, because a garbled one has still said stop, or
  no. Peer text is sanitized where it enters a message.
- `channel.js` seals and opens. The nonce is a per-direction counter that
  only the `Nonces` class can advance. Sending and receiving use different
  keys, and the constructor refuses the same key for both. A frame that
  fails to open ends the channel for good, so a caller cannot skip it and
  carry on. `wipe()` zeroes both keys, and a Channel refuses keys that are
  already zero, so keys are single-use.

`transfer.js` never builds a frame itself and has no unsealed mode:
`sendFile` and `receiveFile` refuse to start without keys.

## The transfer: `transfer.js`

**Sending.** `sendFile` opens the file once, and the size, the hash, the
prefix digests resume needs, and every byte sent come through that one
descriptor (W15b). `sendStream` takes any readable and offers `size: null`,
computing the digest as it reads, and only if `stream` was negotiated.
Both go through one state machine (`offerAndSend`, `offerSource`), whose
phases are PROTOCOL §4.4's sender states: offered, prefix sent, sending,
awaiting result. Nothing is read from the source before ACCEPT. The sender
honors backpressure, splits a stream's chunks to the declared
`blockSize`, and enters each phase *before* the write that lets the peer
answer, because a transport may deliver the answer inside that write.

**Receiving.** `receiveFile` answers an offer in a fixed order, cheapest
first: validate the manifest (a closed field set, an 8 GiB default cap)
and the name; ask `onOffer`; check free space; open the partial; ACCEPT.
So a declined offer creates nothing on disk. Every refusal on that path
goes to the sender as DECLINE with a code. While receiving, it refuses a
chunk over `blockSize` or past the declared size, pauses the socket when
the disk falls behind, and times out a sender that stops. The bytes go to
`<name>.part`. When the digest matches, the file is published with
`link()` then `unlink()`, which fails rather than replacing an existing
file, so a taken name lands as `name (1).ext`. On a filesystem without
hard links it falls back to check-then-rename, and says so as `published`.
RESULT goes out only after the publish.

**Resume.** With `resume` negotiated and a declared size, `receiveFile`
first looks for `<name>.part`. It is reopened with `O_NOFOLLOW`, and it
must have one link and be no longer than the offer. It is re-hashed up to
the last 1 MiB boundary and proposed as `ACCEPT{n}`. The sender answers
with PREFIX, the digest of its own first *n* bytes, from digests it
recorded while hashing, so the skipped part is never re-read. On a match
the partial is adopted from *n*; otherwise it is truncated to zero, and
the same connection starts over (PROTOCOL §7.5). Only an interruption
keeps a partial; a cancel, a mismatch, or a protocol error discards it.
A reopened partial is never touched before the final ACCEPT.

**Timers.** Manifest 30 s, progress 60 s, the receiver's answer 5 min,
RESULT 2 min. All are `ERR_STALLED`, and all are listed by state in
PROTOCOL §4.4.

**Progress.** `onProgress({ bytes, total })` fires once per chunk,
unthrottled, with a guaranteed first event at 0 and a final one at the
total (`total` is `null` for a stream). It is hand-off, not delivery:
`onCheckpoint` is delivery, and the sender's promise resolving is
confirmation.

**Cancel.** An `AbortSignal` covers the join and the transfer. The side
that aborts writes CANCEL, waits up to 250 ms for it to flush, and rejects
with `AbortError`; the peer rejects with `ERR_CANCELLED_PEER` and the
reason. Without that flush window the peer would see a reset, which looks
exactly like a dead hole punch. How long a cancel takes to land was
measured, not estimated (PROTOCOL §8.2): about one chunk when the receiver
cancels, and several times that when the sender does, because the
sender's CANCEL queues behind whatever the kernel already buffered.

## Names: `names.js`

A manifest's name reaches two sinks, and `names.js` owns both, so that
they cannot disagree:

- **The terminal.** `displayName` (and `displayText`, for a whole line)
  escapes control and bidi characters as `\uXXXX` rather than removing
  them, so the reader can see something was there, and it never throws:
  the moment a name most needs printing is when it is being refused.
- **The filesystem.** `safeWriteName` refuses traversal, control and bidi
  characters, empty and over-long names. It transforms what is merely
  awkward: `<>:"|?*`, trailing dots and spaces, and Windows device names
  on Windows only. `safeOutputName` in `transfer.js` then asserts that the
  resolved path stays inside the output directory.

## Errors

Every failure a caller sees is a `TransferError` with a `.code`, and the
codes are PROTOCOL §10's. Automation, tests, and `scratch-trials.js` switch
on the code, never on the message. A local abort uses Node's own
`AbortError`/`ABORT_ERR`, so generic abort handling still works.

Three more codes say why one *candidate* was discarded, not how a drop
ended: `ERR_PAKE_CONFIRMATION`, `ERR_SID_REUSED`, and
`ERR_REPLY_UNANSWERED`. They are what `swarm.js` counts. Two kinds of error carry a code without being a
`TransferError`: frame.js's `FrameLengthError`, which keeps that module
free of the engine's vocabulary, and the handshake's per-candidate
refusals. Everything branches on `.code`, so that is the contract.

## The CLIs

- **Receive.** `ad-hal-receive` generates a code (or reads one from the
  prompt or stdin) and shows it, with its QR symbol, once announced. Each
  offer is shown with its name, size, SHA-256, and any resume, and the
  person is asked. `--yes` skips the question; with no terminal and no
  `--yes` the offer is declined. A name that would run when opened is
  warned about either way. The receiver also prints a line when
  candidates fail confirmation repeatedly (3) or go silent (5), and again
  at each doubling.
- **Send.** `ad-hal-send` takes the code from the prompt or stdin, and from
  argv only with `--code-on-argv`, which streaming from stdin needs.
- **Both** say they are not anonymous, print every error through
  `report.js`, and turn the first Ctrl-C into a clean cancel (the second
  exits at once).
- **Environment:** `ADHAL_BOOTSTRAP` (validated in `env.js`, and never
  echoed), `ADHAL_JOIN_TIMEOUT` (receiver 30 s, sender 120 s),
  `ADHAL_REFRESH_INTERVAL`, `ADHAL_MAX_SIZE` (`0` is no limit),
  `ADHAL_NO_PROGRESS`, `ADHAL_QR_WIDE`, and `ADHAL_INSECURE_OPAQUE_CODE`.

The loopback CLIs, `send.js` and `receive.js`, are test-only. They are not
in `bin`, and `--help` says so.

## Testing

`pnpm test` runs everything; `pnpm test:fast` (`ADHAL_FAST=1`) skips the
tests marked `slow`, which need a DHT testnet or a child process. `pnpm
typecheck` runs `tsc` over the JSDoc. `pnpm fuzz` runs the fuzz harness at
100,000 iterations per target. [`TESTING.md`](TESTING.md) has the commands
and how to use them, including drops between two machines.

Helpers live in `cli/test-helpers/`, outside `cli/test/` so the runner
does not count them as tests:

| Helper | For |
| --- | --- |
| `duplex-pair.js` | Two cross-wired streams standing in for a socket. Note that it delivers synchronously, inside `write` |
| `sealed.js` | Channel keys for both sides, and a hand-rolled sealed peer |
| `fake-swarm.js` | An in-memory swarm for `acceptOnce`/`connectOnce`, so their candidate rules run without a DHT |
| `test-peer.js` | A hand-played peer on a testnet that does not fall into hyperdht's pairing race |
| `interrupt.js` | A real Ctrl-C to a child process, Windows included |
| `tiers.js` | The `slow` marker |

Beside the behavior tests, three files pin the protocol as a whole:
`state-machine.test.js` (every message in every state, PROTOCOL §4.4),
`negative-vectors.test.js` (PROTOCOL §11), and `fuzz.test.js`.
`security-properties.test.js` pins the security properties of W15, and
the vector files pin the CFRG suite, the code derivation, and the
handshake mapping.

One more check runs by hand: every source file must be text. A literal
NUL or ESC in a string makes `grep` treat the file as binary and silently
skip it.

```
find . -name '*.js' -not -path './node_modules/*' -exec file {} + | grep -v text
```

## Diagnostics: `engine/scratch-*.js`

Standalone tools for questions the tests cannot answer, mostly about real
networks. They are not shipped (`files` in `engine/package.json` is
`src` only).

| Tool | Answers |
| --- | --- |
| `scratch-trials.js` | A success *rate* over N real drops between two machines, with every failure classified: [`MEASURING-TRANSFER-RELIABILITY.md`](MEASURING-TRANSFER-RELIABILITY.md) |
| `scratch-pairing-race.js` | How often, and why, pairing on a shared address is slow: hyperdht's LAN race, with a counterfactual that removes it |
| `scratch-lookup.js` | Whether a topic's announce is visible, and with `--connect`, whether it can be punched |
| `scratch-swarm-dial.js`, `scratch-hs-dial.js` | What Hyperswarm's own discovery and dialing do, including the errors it swallows |
| `scratch-serve.js` | A receiver that keeps accepting, for probing from the far side |
| `scratch-listen.js` | Whether becoming a DHT *server* (listen and announce) works on this network, since a stalled one never even looks up |
| `scratch-cancel-latency.js`, `scratch-fsync.js` | The measurements behind PROTOCOL §8.2 and §8.3 |
