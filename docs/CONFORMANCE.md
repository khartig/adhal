# Conformance

How to check an implementation of the Adhal v2 wire protocol
([`PROTOCOL.md`](PROTOCOL.md)) against this repository's conformance
material: the test vectors, which need nothing but the files, and the
harness, which drives an implementation through real drops over loopback
TCP and checks what it puts on the wire.

The material is in [`conformance/`](../conformance), a private workspace
package that is not published to npm.

## The test vectors

Five JSON files in [`conformance/vectors/`](../conformance/vectors). Each
says where its values came from, in its `source` field, and how it is
encoded, in `encoding`.

| File | What it covers | Where the values came from |
| --- | --- | --- |
| `cpace.json` | CPACE-X25519-SHA512: `prepend_len`, `lv_cat`, `transcript_ir`, the initiator/responder case end to end, and the twelve low-order points for `scalar_mult_vfy` | Transcribed from draft-irtf-cfrg-cpace-14. External: an implementation that does not reproduce them is wrong. |
| `code.json` | §2: a typed or scanned code to its canonical form, nameplate, secret, topic, and QR payload | Generated by this implementation. `blake2b256Abc` is the published BLAKE2b-256 digest of `abc`. |
| `handshake.json` | §3.2: a nameplate, secret, `sid`, both scalars, and both capability sets to CI, ADa, ADb, the generator, Ya, Yb, K, the transcript, the ISK, `mac_key`, both confirmations, and both channel keys | Generated by this implementation |
| `frames-negative.json` | §4.4 and §5: twelve sealed frames a receiver must refuse, as exact bytes under fixed keys, and the code each must be refused with | Generated by this implementation |
| `handshake-negative.json` | §3: the handshake transformations an implementation must refuse, the seven non-canonical `caps` encodings, and the reflection vector | Specified by PROTOCOL.md |

**How far to trust the generated ones.** `code.json`, `handshake.json`,
and `frames-negative.json` were produced by this implementation, so on
their own they pin it rather than prove it. Two things narrow that gap:

- `cli/test/handshake-vectors.test.js` recomputes every derivation above
  the curve arithmetic a second way, from `node:crypto` over byte strings
  it assembles by hand.
- `conformance/src/wire.js`, the harness's own implementation of the wire
  format, shares no code with `engine/src` and reproduces every value in
  `cpace.json`, `handshake.json`, and `frames-negative.json`, and every
  topic in `code.json` (`conformance/test/wire.test.js`). It was written
  from PROTOCOL.md by the same author, so it is a second implementation,
  not an independent one.

Node has no BLAKE2b-256, so `wire.js` carries its own, written from
RFC 7693. At a 64-byte output it is checked against Node's `blake2b512`
on every input length up to three blocks and one byte, which `code.json`
alone could not do: every nameplate there fits in one block.

**The capability encoding**, which every handshake value depends on: each
token matches `^[a-z0-9]([a-z0-9-]{0,14}[a-z0-9])?$`, and the set is
deduplicated, sorted bytewise ascending, and joined with `,` (0x2c), at
most 128 bytes in all. The empty set is zero bytes. v2 defines two tokens,
`resume` and `stream`. A peer's `caps` are refused unless they are exactly
this encoding, and are hashed into the transcript as received.

## The harness

The harness is a reference peer. It listens on 127.0.0.1, starts your
adapter, which connects to it, and plays the other side of a drop: the
sender when your implementation receives, and the receiver when it sends.

It is a party to the handshake, so it derives the same keys as your
implementation and can open every frame you send. Every frame is checked
as it arrives:

- its declared length against §5's bounds (17 bytes to 1 MiB);
- that it authenticates under your direction's key, with the next nonce
  counter and its own length header as associated data;
- that its type is defined;
- that its body is a JSON object, for every type but CHUNK.

Each scenario then checks what the frames mean. 81 scenarios, in four
groups:

- **The five of §11, in both roles:** the handshake, a normal transfer
  (including an empty file and chunks of the largest size a frame can
  carry), a cancel from each side, a resume (a matching prefix, a
  mismatched one, and, without `resume` negotiated, no partial kept), and
  a streaming transfer (including a stream offered without `stream`
  negotiated).
- **The negative frame vectors**, sealed under the live session's keys
  rather than the fixed ones, against your receiver.
- **The handshake vectors**, against your receiver and your sender: a bad
  confirmation, capabilities stripped from HELLO and from REPLY in
  transit, a reflected confirmation, a v1 opening, a sealed frame where
  HELLO belongs, out-of-bounds lengths, and each non-canonical `caps`
  encoding. A side that refuses must send nothing after the refused
  message. A receiver that refuses REPLY sends no CONFIRM.
- **The state machine's refusals (§4.4)**, against both roles: off-boundary
  and out-of-range resume offsets, an answer to PREFIX naming a third
  offset, DECLINE and `ERR_DROP_TAKEN`, RESULT that is early, wrong, or an
  error, CHECKPOINT that goes backward, gets ahead, or arrives without
  `resume` negotiated, END on a sized transfer, chunks over `blockSize` or
  past the size, a wrong digest, and manifests outside §4.0's closed
  field set.

`node conformance/src/cli.js --list` prints every scenario with the
sections it checks.

**Not covered, and why:**

- A repeated `sid` and the attempt cap need many connections to one drop.
  The adapter contract is one connection, and both are the join's
  behavior, not the stream's.
- Timeouts (`ERR_STALLED`) would make a run take minutes.
- CHECKPOINT cadence is a receiver-local tuning decision (§8.3). A
  CHECKPOINT is checked for validity whenever one arrives, and is never
  required.
- The topic and discovery: a byte stream cannot test them, and
  `code.json` covers the derivation.

## The adapter contract

An adapter is a command that runs your implementation for one connection.
The harness appends a role and its arguments:

```
<adapter...> receive --connect 127.0.0.1:<port> --dir <dir> [--cancel-after <bytes>]
<adapter...> send    --connect 127.0.0.1:<port> --file <path> [--stream] [--cancel-after <bytes>]
```

- The code is in the environment, never on argv:
  `ADHAL_CONFORMANCE_NAMEPLATE` and `ADHAL_CONFORMANCE_SECRET`, both in
  canonical form.
- **Connect** to the address given, run the v2 handshake for the role,
  then the transfer. One connection and one attempt.
- **receive** writes into `--dir`, accepting every offer that passes its
  own checks, and resumes from `<name>.part` there when it can.
- **send** offers `--file` under its base name. With `--stream` it offers
  the file as a stream of unknown length (§4.3).
- **--cancel-after** cancels locally, sending CANCEL, once the transfer
  has moved at least that many bytes.
- **The outcome:** as it exits, the adapter writes exactly one JSON line to
  stdout, `{"ok":true}` or `{"ok":false,"code":"<code>"}`, with a §10 code,
  or a per-candidate code for a failed handshake. It exits 0 on success,
  nonzero otherwise. Anything else goes to stderr, which the harness
  quotes when a scenario fails.
- **Let the connection go gracefully.** After a failure, end the write side
  and keep reading until the peer closes, briefly, before destroying the
  socket. On TCP, a socket destroyed with unread bytes closes with a RST,
  and a RST can make the peer discard the CANCEL or RESULT you just sent.
  The harness measured exactly that against this repository's own adapter
  (3 of 60 receiver cancels lost before the fix, 0 of 180 after).

[`conformance/adapters/engine.js`](../conformance/adapters/engine.js) is
the adapter for this repository's engine, about a hundred lines.

## Running it

From the repository root, against this repository's engine:

```bash
pnpm conformance
```

Against yours:

```bash
node conformance/src/cli.js -- <your adapter command...>
node conformance/src/cli.js --only '^S-' -- <your adapter command...>    # sender scenarios only
node conformance/src/cli.js --json -- <your adapter command...>          # one JSON object per scenario
```

It exits 0 when every selected scenario passes. A run takes about 40
seconds. `pnpm test` runs the same scenarios against the engine, one test
per scenario, along with `wire.test.js` and the planted-bug test below.

## What passing means

Passing means the implementation interoperated with a second
implementation of the wire format on every scenario above, and refused
everything the scenarios say it must. It does not mean the implementation
is secure. The harness checks behavior on the wire, not how keys are held
in memory, whether scalars are reused across connections, or anything
§12.3 lists as not claimed.

**The harness's own checks are tested.** `conformance/test/planted.test.js`
plants eleven bugs, one per kind of check, in a copy of the engine and
requires the scenarios that check each one to fail. The bugs are a nonce
counter off by one, the associated data dropped on each side, the
confirmation labels swapped, the capabilities sorted backward, the
declared `blockSize` wrong, the receiver's `blockSize` check removed, a
resume proposal off the boundary, a wrong PREFIX digest, a wrong RESULT
digest, and a local cancel that sends no CANCEL. Several of these the
engine's own suite cannot see, because the engine would be wrong the same
way on both ends. The backward caps sort is the clearest: the engine checks
a peer's caps by re-encoding them, so it would accept its own backward
encoding forever.
